# 04 · Product gaps and risks

Priorities describe a complete, dependable single-household product. They do not authorize implementation or changing dry-run. **P0** before relying on the complete product / enforcing; **P1** next everyday value; **P2** optional expansion. Effort S ≈ one focused task, M ≈ 2–4, L ≈ multiple backend/UI tasks plus deployment verification; not elapsed-time promises.

## Ten highest-impact findings for review

1. P0: Add a real administrator login; private HTTPS does not authenticate dashboard users.
2. P0: Give the Agent sole serialized router ownership after preserving existing direct actions in migration.
3. P0: Persist heartbeat and operation receipts so Saved can be distinguished from Applied.
4. P0: Verify Internet/LAN counters and correct GB formatting before leaving dry-run.
5. P0: Expose per-feature safety and claim ownership; releasing one claim may leave a restriction.
6. P0: Back up the DB and Data Protection keys together and rehearse restore.
7. P1: Make Home and Device detail the daily phone workflows.
8. P1: Add a distinct household ISP budget and configurable billing cycle.
9. P1: Build temporary pause as an expiring claim, preserving existing limits.
10. P1: Split Home into routes and bounded queries, with mobile/accessibility regression coverage.

## Evidence boundaries / design risk

- Phase 5 status and actual Rules files supersede CLAUDE.md's stale “T7 planned” sentence. Rules are implemented, still not live-verified. Phase 3/4 API and reconciliation sections remain plans, not deployed capability.
- Main wireless writes, IoT password, coupling, reboot, T8 counters, HTTPS/Android delivery and enforcement restoration need the checks in their original docs. Visual redesign cannot certify them.
- Protected devices currently skip automatic quota/rule Throttle/Block; manual actions and wireless changes are separate. Product-level promise “never blocked” requires extending all entry-point guards and explaining network-wide actions.
- Authentication/recovery needs a security design review; recommendation is a scoped product direction, not a completed threat model. No biometric, tailnet identity or PIN-only access is silently assumed.
- Unknown/missing data must remain unknown. Fake prototype rows and mock confirmations provide interaction review only.

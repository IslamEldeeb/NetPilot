# Usage, household ISP budget and temporary actions

Batch C implements design tasks T15a–T15c and T16a–T16c. `/usage` and `/` use the same saved-data projection. They never refresh or write to the router. `/legacy` retains every existing tab and router operation.

## Usage and budget

- Day, Monday–Sunday week, calendar month, selected date and one/all device filters. The 30 daily bars end on the selected date; the expandable table provides exact byte counts and explicit gaps. No hourly samples are inferred.
- Calendar-month totals retain the existing authoritative live/monthly counters, even where old daily history is absent. Weeks and non-calendar billing cycles sum saved daily history plus today's matching live state. Missing devices retain their MAC and an unknown category; missing days stay unobserved. Category rankings, device rows and CSV totals share one projection.
- Decimal GB means 1,000,000,000 bytes. CSV exports the displayed period/filter, ISO date boundaries (end exclusive), timezone, identity, exact Internet/excluded-LAN bytes, decimal GB and confidence. Values are quoted, embedded quotes escaped, and spreadsheet formula prefixes neutralized. The download is generated in-page without a router call.
- Set/edit/remove the optional household ISP budget in the Usage sheet. It stores decimal whole bytes and billing day 1–31 in a new `household_budget` LiteDB collection. Boundaries clamp independently to each month's final day, in the configured `UsagePeriodClock` timezone (Africa/Cairo by default). This does not alter calendar Day/Month quota or rule periods, their base caps, or their claims. No household cap appears before configuration.
- Billing-cycle amounts show recorded usage and explicitly disclose incomplete history. Historical router bytes are not reclassified as Internet or LAN. Excluded-LAN totals count both endpoints and remain estimates until the live counter/path experiment is complete.

## Forecast confidence

The estimate divides remaining household cycle budget by the mean Internet bytes from eligible completed days in the previous seven days. It requires at least three eligible days, known cycle-day coverage, a healthy Agent and a recent successful router read, without an unresolved LAN-source outage. It never triggers enforcement. At 214 of 300 GB and 17.2 GB/day, it reports about five days remaining.

Old daily documents have no sampling evidence and therefore default to ineligible for forecasting; their totals and charts remain available. New daily history is eligible only when the first poll was within 15 minutes of local midnight, polling had no gap over 15 minutes, finalization followed the previous poll within 15 minutes on the next local day, and no counter reset or LAN-source failure was observed. Custom slower polling and Cairo's skipped midnight at DST onset can conservatively exclude a day. These checks describe sampling coverage, not billing-grade counter accuracy. Missing per-device history and unverified router counter behavior remain limitations.

## Quick actions and Agent ownership

The shared sheet on Home and device detail offers pause, symmetric Kbps throttle, and a decimal-GB bonus on a named current Day or Month quota. Restrictions target one device or a category, with 15/30/60/custom minutes (1–1440), target count and protected-skip preview. Bonus requires a configured cap for that device and period; it changes only `QuotaPeriodState.ExtraAllowanceBytes`, atomically and once per dashboard request ID. It does not remove independent rules, other quota periods or manual blocks. Expired period submissions are rejected.

Temporary pause/throttle is persisted in the existing `action_claims` collection, with additive expiry, pending and dry-run fields. Existing documents default to their prior nonexpiring, effective behavior. New requests are pending until the Agent processes them; retries while saved do not reset an active claim or move its expiry. The Agent checks protection again, composes with all other claims (block wins, otherwise lowest Kbps), and uses the existing block token/prior-limit restoration mechanism. Base device/category policies are preserved. Expiry runs on the first successful Agent tick after the saved deadline, including after restart; a failed restoration retains pending state for retry. One failed target does not prevent processing other temporary targets. Temporary errors are isolated from quota/rule evaluation and recorded in the heartbeat.

`NetPilot:TemporaryActions:ForceDryRun` defaults to **true** in both hosts; Docker exposes `NETPILOT_TEMPORARY_FORCE_DRYRUN=true`. The sheet displays the server mode without an activation toggle. Preview claims never restrict the router or capture restoration state. Changing server configuration does not promote previously saved preview claims to live actions; new requests are required. Forcing dry-run also retires existing live temporary claims through Agent reconciliation. Leave this setting, quota dry-run and `NETPILOT_RULES_FORCE_DRYRUN` enabled until usage/T8 and recovery are verified. The existing rules forced-dry-run default is unchanged.

The sheet describes approximate next-tick timing from `NetPilot:PollIntervalSeconds`; saves are not router acknowledgements. Expiry counts from save, so a short request may end before an offline Agent returns. Existing direct manual router paths remain only on their existing screens. Individual quota/rule release controls remain on device detail. Temporary requests currently end through their timer; an early-release UI and favourites are outside this batch's requested scope.
